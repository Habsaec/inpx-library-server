# Performance and event-loop rules

Part of the INPX Library Server agent spec. The rules every task must obey are in
[`AGENTS.md`](../../AGENTS.md); this file is the detailed reference of one subsystem.
Read it before changing that area and update it in the same commit as the code.

Scope: what may not run on the request thread of a 700k-book library

---

## Rules

| Rule | Meaning |
|------|---------|
| Favorites pages stay cheap on cold caches | Reported on a 2-core / 3 GB Docker host: `/favorites` stalled the loop 2.6 s (books), 8 s (5 series), 75 s (55 authors) because every favorite was counted / ranked through `active_books` (random reads of thousands of book rows). Now `getFavoriteAuthors` / `getFavoriteSeries` (also `/api/favorites`, Android) take `bookCount` from `authors.book_count` / `series_catalog.book_count` and show an author by his portrait (`/api/authors/portrait`) or a placeholder with two letters in the order the name is written on the card — «Головачев Василий» → `ГВ`, «Лукас Дженни» → `ЛД` (`authorInitials` in `src/genre-map.js`) — `coverBookId` is now always null — and a series by the covers of its first six volumes (`previewBookIds`, `FAVORITE_SERIES_COVERS`: lowest `series_no` first, unnumbered last, ordered over `book_series` rows only, the first 24 checked against `active_books`). Android: favorite author rows no longer pass `coverBookId`. `getFollowingNewBooks` / `getFollowingNewCount` choose a plan by volume (`followingFavoritesDriven`: favorites' `book_count` sum × 4 < books in the 90-day window → start from the favorites' books, otherwise from the recent window, whose books sit in neighbouring pages, and test favorite membership by book id); the badge memo is 10 min (cleared by favorite changes and visits). `getReadBookIdSet` no longer builds the fully-read series set (`getFullyReadSeriesNames`, the expensive half, is lazy: only the series view needs it). Rule: a per-favorite correlated query over `active_books` must not scale with the size of the favorite's catalog |
| Heavy aggregates stay off the event loop | `src/services/query-worker.js` + `query-pool.js` (`queryAsync(sql, params, { mode, fallback })`): a persistent read-only worker for GROUP BY / COUNT scans (filtered catalog totals via `warmBrowseTotal`, genre options, authors/series by genre, OPDS title prefixes `warmOpdsTitleQuery`, following window); routes `await` the warm-up, then the sync function hits the memo. `getStaleOrScheduleAsync` (cache.js) = stale-while-revalidate for such results. Per-language counters: `catalog_lang_counts` kind 0 (id 0) = books per language, used by `listLanguages`, the language facet and authors/series by language (`listEntitiesByLanguage*`); facet value `unknown` is NOT a language code and keeps the SQL path. Planner tricks: `CROSS JOIN` to pin the outer loop on a sort index, `+b.lang` to stop `idx_books_lang` being chosen for novinki, range predicates instead of `LIKE ? \|\| '%'`. OPDS authors/series prefix lists read `book_count`/`search_name` ranges (memo 30 min). Following (`/library/following`, badge): one shared 90-day window (`followingWindowBooks`, built on the worker, prewarmed at boot and after indexing) filtered in JS per user. Known open: a 1–2 letter free-text search still ranks the whole FTS match set (~0.8–1.8 s). Server only — Android needs nothing |
| Event-loop / paging rules from the 2026-11 audit | `mergeSeriesQualifierDuplicates` is skipped while meta `series_qualifier_merge_fp` (`indexed_at` + `series_catalog` count / max id) is unchanged — it used to redo ~17k author lookups at every boot (≈ 60 s of stalls on a cold disk); its surname reads go through the query worker, one read per base series per pass. Browse by genre (`genreDrivenBrowse` in `src/inpx.js`): when the selected genres hold ≤ 8000 books (≤ 100 000 for OFFSET ≥ 240 and for every COUNT) the page is read from `book_genres` (`DISTINCT` subquery — keep it, a flattened one is 10× slower — `CROSS JOIN books`) and only those rows are sorted; bigger genres keep the sort-index walk — unless a narrowing filter is set too (rating, year, format, `hasSeries`; `GENRE_DRIVEN_NARROWING_RE`): hits are then rare and the walk covers most of the catalog (a pinned smart shelf «sf_action + оценка 5 + в серии» took 7 s warm, 100 s on a cold disk at every start), so such a page also reads the genre's list up to 100 000 books. The total memo key stays on the default WHERE. `hasSeries` filter is a scalar subquery `(SELECT 1 … LIMIT 1) IS [NOT] NULL`, never `EXISTS`: SQLite 3.51 turns a single-table EXISTS into a join and counts OFFSET before that test, so page 2+ repeated earlier books when another filter was set — do not write a single-table `EXISTS` into a paged query that walks a sort index. `getBooksFtsStatus`: an expired healthy snapshot is served while both COUNTs rerun on the query worker; the first call after boot on a catalog with rowid ≥ 100 000 answers from cheap probes (provisional counts = max row ids) — `force: true` is still exact and synchronous. `warmFb2cngVersion()` (boot) asks `fbc --version` asynchronously. `warmSmartShelfTotals(username, { home, pageSize })` is awaited before smart-shelf first pages (`/`, `/api/home/shelves`, `/shelves`, `/api/smart-shelves?preview=1`); besides the totals it reads each shelf's first page on the query worker (`warmBrowsePage` → `_browsePageMemo`, taken once by the next `searchBooks` of the same SQL + params, 2 min, cleared with the runtime caches) unless `getSmartShelfFirstPage` already has it — the genre-list page of «sf_action + оценка 5 + в серии» is 0.4 s warm but froze the server for 55 s on `GET /` right after a restart on a cold disk. Batch ZIP (`streamBatchZipArchive`): at most 4 books are resolved / queued at a time (slot freed on archiver `entry`), a closed connection stops the workers. Every `async (req, res)` route handler is wrapped in `asyncHandler` (Express 4 does not catch rejections: an OPDS feed that threw left the client waiting for the timeout); a test that reaches the query worker must call `stopQueryWorker()` in its teardown or the test process never exits. `/health/perf` and `/api/health/archives` need an admin session (`/health`, `/ready`, `/api/index-status` stay public). Server / web only — Android needs nothing |

## Static assets

Web static assets (`public/sw.js`): the Service Worker is **network-first** for `STATIC_ASSETS` (`fetch` with `cache: 'no-cache'`, install uses `cache: 'reload'`); the SW cache is only an offline fallback. A cache-first SW combined with `immutable` headers served a stale `position-sync.js` next to a new `reader.js` and the web reader hung on «Загрузка книги…» (`SyntaxError: does not provide an export`). `node scripts/build-assets.js` bumps `CACHE_NAME`. URLs whose `?v=` equals `STATIC_ASSET_VERSION` (content hash in `src/templates/shared.js` — every file linked with it must be in `computeStaticAssetVersion`) are served `public, max-age=31536000, immutable`, and the SW lets the HTTP cache answer any `?v=` URL; files without `?v=` (foliate modules, `position-sync.js`, `reader-shared/*`) stay `no-cache`. JS/CSS are precompressed once in memory (brotli q11 + gzip 9, `src/services/static-precompress.js`, keyed by mtime/size; the first request falls through to on-the-fly compression). The client dictionary is `/i18n/<ru|en>.js?v=<hash>` (`window.__UI_I18N__`, loaded `defer` before `app.js` / `reader.js`), no longer inline JSON in every page. Minified `app.min.js` / `styles.min.css` are served unless `NODE_ENV=development` (a `.min` older than its source is never used).
